# CampusHub 面试技术笔记

## 本地MVP演示（5～8分钟）

准备和停止命令统一见 [README](../README.md)，验收事实见 [C-04报告](verification/m1.4-c-04.md)。演示前检查测试库服务、8080、5173和微信编译；使用新的活动标题与未来时间，不依赖过期验收夹具。

1. **架构，约1分钟：** 展示后端Controller → Service → MyBatis Mapper → MySQL分层。Vue管理端与原生TypeScript小程序访问同一Spring Boot服务；业务身份由Session principal决定，不信任客户端角色/userId。
2. **活动管理，约1分钟：** 组织者在Vue登录，创建/编辑草稿并发布。指出DRAFT → PUBLISHED → UNPUBLISHED → PUBLISHED状态机、已发布冻结和version冲突保护。
3. **双端闭环，约2分钟：** 微信学生搜索新活动、查看详情、报名和我的报名；Vue刷新名单展示真实人数。微信取消后Vue人数减少，重新报名后人数恢复，仍为同一报名记录。
4. **权限与下架，约1分钟：** Vue下架，学生列表隐藏、详情不可浏览；重新发布后历史记录和人数保持。说明Session轮换/退出/空闲失效、CSRF和角色/资源归属由后端检查。开发演示账号不是正式微信登录。
5. **事务和证据，约1～2分钟：** 打开RegistrationService与RegistrationIT，解释活动行锁、READ_COMMITTED、唯一(activity_id,user_id)、报名version以及计数与明细同事务。展示C-04真实MySQL并发测试和最终SQL证据，说明为什么跨活动首次INSERT也需要死锁回归。有限并发回归不等于压力测试或吞吐量指标。

若工具卡顿，展示已保存的验收记录并明确这是历史证据；不要把录像/截图称作现场实时成功。面试结尾说明范围：本地MVP可演示，正式微信身份、真机、部署、实时撤权及开发依赖风险仍需独立处理，不宣称生产就绪。

## M1.3：报名、取消与并发事务

实际代码入口：`RegistrationService.change`、`RegistrationMapper`、V4；真实验证入口：`RegistrationIT`。测试规模和最终结果以 [验收报告](verification/m1.3-registrations.md) 为准，不将这些有限并发用例称为压力测试。

**如何保证不超卖？** 每个报名/取消事务先锁活动行，再处理该学生报名行。名额占用使用 `registered_count < capacity` 条件更新，数据库还有 `0 <= registered_count <= capacity` CHECK。报名 INSERT/UPDATE 和人数增减处于同一个 Spring 事务，异常向外传播，不吞异常返回成功。

**为什么还要唯一约束？** 行锁负责协调业务操作；`UNIQUE(activity_id,user_id)` 是数据库最后一道约束。取消不删记录，重新报名复用 CANCELLED 行，因此一人一活动只保存一条当前状态记录。没有声称这是完整操作审计日志。

**幂等与取消后重报如何兼容？** 同状态重试不增加/释放名额。真正切换状态必须匹配报名 version：NONE/0 → CONFIRMED/1 → CANCELLED/2 → CONFIRMED/3。旧取消请求 version=1 此时返回冲突，不能取消 version=3 的新报名。无需 Redis 或分布式锁；客户端先读状态，写入时携带版本。

**为什么锁后才检查时间？** 线程取得锁可能已经跨过报名截止时间。必须在获得活动行锁之后读取当前时刻，再判断窗口；测试持有活动锁直至截止以后，等待中的报名必须失败。

**只测同一活动并发够吗？** 不够。独立审查发现 RR 下不同活动首次报名也会因缺失唯一键的 gap lock 互相阻塞。真实复现方法是让两次插入在已锁缺失键后同步启动；一条事务发生死锁。修复仅将报名写事务明确为 READ_COMMITTED，保留活动锁、唯一约束和事务；测试还读取真实连接的隔离级别。这里的 RC 不是放弃一致性，而是把同活动业务串行化交给显式活动行锁，避免无必要的缺失键范围锁。

**如何兼容活动管理？** 保持 DRAFT/PUBLISHED/UNPUBLISHED 状态机；已发布字段仍冻结。编辑、发布、下架与报名共用活动行锁，编辑容量不能小于有效人数。活动 version 只用于 M1.2 编辑/状态操作，报名 version 独立，避免报名流量使组织者编辑版本不断失效。重发布不写人数。

**计数器是否会成为两份事实？** 明细和计数确实是冗余存储，代价是必须统一事务和写入口，并用 SQL 检查计数等于 CONFIRMED 明细数。直接手工 SQL 绕过服务仍可能破坏二者相等，CHECK 只能保证数值范围，不能跨表计数。本阶段未引入自动对账修复。

**怎么证明事务和并发正确？** 独立 MySQL CONNECTION_ID + CountDownLatch 同步竞争；逐个验证最终数据库人数、明细数、唯一性和容量，不只看 HTTP 200 数量。使用真实外键和 CHECK 违规验证回滚；这些是实际 MySQL 错误，不是 mock 抛异常。既验证服务事务，也验证真实 Session/CSRF HTTP 请求。

**权限怎么控制？** 用户 ID 来自服务端 principal；组织者名单查询校验活动归属，管理员沿用当前全活动范围。应用与迁移账号分离，新表只授 SELECT/INSERT/UPDATE。个人历史只返回报名元数据，活动下架后不能通过报名接口读取非公开活动内容。

**范围限制：** 单 MySQL 实例内事务；没有吞吐量或性能提升结论；未实现分布式系统、候补、签到、通知或完整状态历史。Vue和原生小程序已在后续阶段实现，见上方MVP演示。会话角色快照继承M1.1，实时撤权仍属后续范围。
