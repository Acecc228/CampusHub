## 业务契约

- 学生身份仅取 Session。管理员范围延续 M1.2 全部活动，组织者仅本人活动。
- 报名窗口为 registrationStart <= now < registrationEnd，且活动为 PUBLISHED。取消允许到活动开始前（now < startTime），包括下架期间；开始后不得取消。
- 每活动/学生一条记录，状态 CONFIRMED/CANCELLED；未建立记录显示 NONE、version=0。首次报名 version=1，之后每次状态变化 +1。取消后重新报名复用记录，重新检查全部条件。
- POST `/api/v1/activities/{id}/registrations` 报名；POST 同路径 `/cancel` 取消；请求 `{version: 非负整数}`。当前状态已等于目标且请求版本不超前时，返回当前状态，不修改名额。状态需变化时必须版本相等；旧取消/报名在跨生命周期重试时返回 409，不影响新状态。客户端需先读状态取得版本。
- GET `/api/v1/activities/{id}/registration` 返回自己的状态；非公开活动仅已有报名者可查看自己的记录，不返回活动内容。
- GET `/api/v1/student/registrations` 返回自己的记录；GET `/api/v1/manage/activities/{id}/registrations` 返回授权名单。page 1..10000，size 1..100。列表只含报名 ID、活动 ID、用户 ID、状态、版本、时间，不含账号、密码、联系方式或未公开活动详情。
- 活动详情保留 M1.2 字段，增加 registeredCount、remainingCapacity、myRegistration。管理详情/列表也返回人数，列表不逐项查询个人状态。
- 400 参数错误，401 未认证，403 角色或归属拒绝，404 不可见或不存在，409 状态/时间/容量/版本冲突。重复请求为 200。

## 数据与并发

V4 新建 activity_registration，UNIQUE(activity_id,user_id)、两个外键、状态/版本 CHECK、个人列表与活动名单索引；不级联删除。activity 新增 registered_count（初始 0），CHECK 0 <= registered_count <= capacity。历史迁移不变。

选择持久化计数器以便单行 CHECK 保证容量上限，报名明细与计数在同一事务写入，取消只在 CONFIRMED -> CANCELLED 时减一。与每次 COUNT 明细相比读取更直接；代价是必须验证计数与有效记录始终一致，不增加第二份容量。

所有状态变化按 activity 行锁 -> registration 行锁顺序。报名/取消事务明确 READ_COMMITTED，使用 SELECT FOR UPDATE 获取最新数据，获得锁后才检查时刻。M1.2 编辑也先锁 activity，并检查新容量不得小于人数；保留现有活动状态机和 version 更新语义，报名不改变活动编辑版本。发布/下架不写人数。

审查修正：默认 RR 下，不同活动的缺失报名键可同时持有同一个 gap 锁，随后 INSERT 死锁。已用测试专用 MyBatis 插入前屏障、真实 SQL、两个实际服务事务复现；采用 RC 避免该查询的 gap 锁，活动行锁继续保证业务串行化。读取列表/详情保持原默认隔离级别，保证同一事务内计数/列表或人数/个人状态快照一致。未来如外层事务组合调用报名服务，外层须同样使用 RC；Spring 加入既有事务时不会覆盖外层隔离级别。

报名名额条件更新与记录写入属于同一 Spring 事务；异常传播触发回滚。独立连接的并发测试验证最终人数、唯一记录、状态和容量，不以 HTTP 成功次数代替一致性。测试使用数据库 CHECK/FK 真实失败验证中途回滚，不引入生产故障开关。

## 权限与数据保护

授权前检查当前账号/Host、完整既有表级权限及新表结构；授权后完整 SHOW GRANTS 比对，确认仅报名表增加三项权限。activity 已有 SELECT/INSERT/UPDATE 足够，无需新增权限。两个应用均无报名表 DELETE/DDL/跨库权限。迁移仍用独立 migrator。

所有业务测试仅写 campushub_test。M1.3 新夹具带随机标识并保留为证据（新表不授 DELETE）；不删除既有数据。M1.1/M1.2 原测试仍只清理自身新夹具。原 probe、历史 checksum、开发库业务数据保持不变。
