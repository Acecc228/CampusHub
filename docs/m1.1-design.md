# M1.1 三角色认证设计与实施计划

用户于 2026-10-19 授权自主完成设计、编码、迁移、测试。仅实施认证/RBAC，不进入 M1.2。沿用当前未提交工作区，不建立缺少既有文件的新 worktree，不提交或推送。

## 决策

- 采用 Spring Security 7 Session + CSRF；比较过 JWT（撤销需额外状态）和自建 opaque token（重复实现生命周期），当前单实例开发环境使用框架 Session 最简单。30 分钟空闲超时、登录轮换 session ID、退出销毁会话，重启失效。
- Flyway V2 新增 `app_user`、`app_role`、`app_user_role`。稳定内部用户 ID，唯一 login_name，display_name，enabled，demo_account，nullable password_hash；角色唯一代码及外键关联。V2 只初始化三种角色，不包含演示用户和密码。
- 演示用户通过独立显式 `-Apply` 配置脚本写入，两库使用不同随机密码；PBKDF2-HMAC-SHA256，16 字节随机盐、600000 次迭代、256 位输出，与 Spring 编码器兼容。原文仅存放现有受限 secrets 目录，不输出或入库。重复执行只核实已有账号、密码及角色，冲突失败，不覆盖。
- app 对三个认证表仅 SELECT；test-app 对用户/关系表 DML（真实测试需要），角色表 SELECT。迁移/配置使用独立 migrator，授权使用既有 root 客户端，不传入业务进程。
- 默认 `campushub.auth.demo-enabled=false`。只有显式启用、活动 profiles 非空且全部属于 dev/test、监听 loopback 三条件同时满足才启用演示认证。prod、混合 prod/dev、未知/默认环境强制启用均启动失败。日常运行脚本使用专用 `-EnableDemoLogin` 开关；生产调用拒绝该组合。
- 使用 DaoAuthenticationProvider、数据库 UserDetailsService、SecurityFilterChain lambda DSL。只接受账号密码；role/userId 等额外字段不作为身份依据。密码错误/未知/禁用/非演示用户统一 401。
- 框架登录处理器负责保存 SecurityContext、会话轮换与 CSRF token 清除；登录后客户端重新获取 CSRF。GET `/api/v1/auth/csrf`，POST form `/api/v1/auth/demo-login`，GET `/api/v1/auth/me`，POST `/api/v1/auth/logout`。无认证 401，认证后权限/CSRF 不足 403，无重定向 HTML 登录页。
- 微信边界：演示适配器只负责凭据验证；`IdentityService` 将受信任的服务端身份映射为 `CampusPrincipal`（内部 ID、显示名、角色）。未来 wx.login 必须服务端 code 交换并按 openid 映射内部用户，再复用 principal/Session；本阶段不实现微信接口、AppSecret、用户自注册或客户端指定 ID 的认证入口。
- Session 内角色为登录时快照；角色变更需重新登录。当前无角色编辑/封禁业务接口。分布式 Session、正式登录、网络部署、暴力破解限流留待正式认证阶段；演示环境只绑定本机。

## 权限矩阵

| 路径/能力 | 匿名 | 学生 | 组织者 | 管理员 |
|---|---|---|---|---|
| GET 分类、health、CSRF | 允许 | 允许 | 允许 | 允许 |
| POST demo-login | 仅显式 dev/test，且 CSRF 正确 | 同左 | 同左 | 同左 |
| GET auth/me、POST auth/logout | 401 | 本人 | 本人 | 本人 |
| GET student/access | 401 | 200 | 403 | 403 |
| GET organizer/access | 401 | 403 | 200 | 403 |
| GET admin/access | 401 | 403 | 403 | 200 |

三个 access 接口用于实际权限检查，返回当前用户及能力名称，不伪造尚未实现的活动功能。角色没有隐式继承；多角色账号按数据库集合授权。未知匿名路径 401，认证后未知路径 404。dev 文档和 M1.0-C 分类行为保持。
